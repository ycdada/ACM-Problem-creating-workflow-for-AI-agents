# 数学定义与解法设计

在构思、形式化、证明或约束变化时读取本文件。

## 写清定义

把用户已确定的事实与候选想法分开。对现有题目沿用其文档；新题使用 `spec.md` 记录：

- 输入对象、合法范围、单测数量和跨测试用例的总量约束。
- 操作的前提、作用与顺序；元素能否重复，是否区分顺序，空对象是否合法。
- 精确求解目标、最优值或可行性定义、答案唯一性、无解输出及必要的容差。
- 与题意一致的最小实例、边界实例、样例和手算解释。
- 目标复杂度、允许语言和整数范围，尤其是中间值的数量级。
- 待证猜想、尚未确定的语义、已有反例及其影响。

题意有两种合理解释时，给出能区分它们的最小实例，记录待定语义。正式数据和标准答案使用已确定的定义。

## 形成可检查的解法

1. 从定义给出可直接实现的小规模求解法，明确穷举或搜索空间和适用上限。
2. 推导目标算法，写清关键引理、状态含义、转移或贪心选择，以及边界条件。
3. 将证明步骤对应到实现所需的不变量、数据结构和数值类型。
4. 寻找潜在的更简单解法、反例、特殊性质和较慢但正确的算法。
5. 按需要用手算、穷举或小规模对拍检查猜想，明确区分证据方式。发现分歧时先核对定义与双方实现，再修改结论。

证明至少说明算法输出的合法性、目标的正确性或最优性，以及过程覆盖全部合法情形的理由。复杂度按完整输入计数，包含多测试总量、排序、初始化、清空与数值运算成本。

独立解优先使用不同推导或不同算法；同一算法的独立实现可以补充实现核对，但要如实说明独立程度。

## 选择约束和出题目标

结合目标算法、竞争解法、最坏情况和实际测量选择约束。修改约束时同步检查 validator、生成计划、输出语义、数值范围和题面。

将候选题目的特点、可疑套路与可能的非预期解写成待验证项。难度估计注明依据，真实选手盲测与模型估计分别记录。

完成条件：用户要求的设计材料已经写入文件；数学定义与候选结论的界线清楚；证明和复杂度可审查；尚未解决的疑问均有具体实例或待办。若只要求设计建议，到此按本次范围交付。
